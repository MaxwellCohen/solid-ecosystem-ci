Solid streaming hydration harness

← Solid streaming demo

Each test takes a tree with <Loading> boundaries and streams it from the server, in several parts, into an iframe with document.write, so the real HTML parser sees it. The page is written in a random order mixed with hydration, client code finishing loading, re-renders, button clicks, reorders, hiding and showing, unmounts, parts split in two at a random byte, and connections that drop. When everything has arrived, the same tree is rendered from scratch next to it with the same actions, and the two are compared.

A run fails when the hydrated DOM differs from that fresh render (right away, after clicking every button, or after one more re-render), a settle callback ran twice or a ref was missing, an id shows up twice, or anything was logged as an error. Not counted as failures: glitch (an id was visible twice at some step) and kept (share of buttons still the nodes the parser created, so server DOM was hydrated rather than replaced).

This is the Solid port of the Preact/React streaming harness: the same 74 trees and the same schedules and checks (runner.js is shared). Solid has no throw promise, so a gate is an async memo: the server's waits on gate s:<name> and streams its value with the chunk, the client's waits on gate c:<name>, the way code that hasn't loaded yet holds a subtree when hydration reaches it. React-only shapes map to their Solid counterparts (class components and memo() to plain components, useId to createUniqueId, error boundaries to <Errored>, keyed lists to <For>). Some trees test React's contract and fail by design in Solid: a server error with no <Errored> above it fails the render or rethrows on the client instead of being retried there.

Work compared: Solid 2.0.3 from npm, and MaxwellCohen/solid#2 (boundary ranges with <template for> declarative patches, held Reveal patches, batched-swap hydration). Source: harness/ in MaxwellCohen/solid-ecosystem-ci.

Timing

Solid records every flush (one drain of the reactive queue), every async flight and every showing of a <Loading> fallback when its observe build runs. Each tree loads with the shell, hydration right after it, each later chunk 30 ms apart, then its client code arriving. settle is the time from that last input to every fallback gone and every button hydrated (polled every 5 ms, so differences under about 5 ms are noise). flushes, flush ms and runs are the reactive work hydration did; fallbacks counts fallback showings, with how long they stayed. Medians of the recorded loads; lower is better.

The same JSX renders on the server and in the client. <Suspends server="a"> waits on the server until gate a opens, which sends one streamed chunk. <Suspends client="x"> waits on the client until gate x opens, like a lazy component that isn't loaded yet when hydration reaches it. seq lists the actions a schedule may fire.
